## Scope and environment

Local tools: Node.js 25.9.0, npm 11.12.1, Python 3.14.6, Xcode 27.2, and Java 8. The GitHub release workflow uses Java 21 for Android.

## Findings

### High: Provider-backed API routes have no application-level authentication or rate limit

The Express app installs CORS and JSON parsing middleware, but no authentication or rate-limiting middleware. CORS is a browser policy; the CORS callback also accepts requests with no `Origin` header. The cloud chat/agent routes and the desktop computer route can use server-configured provider credentials when present. See [`server/index.js`](../server/index.js#L14), [`/api/agent`](../server/index.js#L340), [`/api/desktop/computer`](../server/index.js#L415), and [`/api/chat`](../server/index.js#L441).

**Impact:** If this API is publicly reachable with server-side AI or voice credentials configured, arbitrary clients can consume those services and drive usage costs. Host-level controls may reduce this risk, but none are defined in this repository.

**Recommendation:** Add server-side caller authentication and per-user/IP quotas for provider-backed endpoints. Keep the health check public if required, and add explicit limits for TTS and token issuance.

### High: Client production dependency audit reports critical and high advisories

`npm audit --prefix client --omit=dev` returned 75 advisories in the production dependency graph. The six critical package entries include `@elizaos/agent`, `@elizaos/app-core`, `@simple-git/argv-parser`, `@whiskeysockets/baileys`, `simple-git`, and `tar`. The direct `@elizaos/capacitor-talkmode` dependency is a beta version; npm's suggested remediation moves to a different major version, so an automatic force upgrade could break native voice behavior.

**Recommendation:** Review the advisory paths and package reachability, then upgrade or replace the affected native-agent/voice dependency chain with device smoke checks. Do not apply `npm audit fix --force` without validating the resulting native integrations.

### Medium: Secondary frontend workspace does not type-check

`npm run build:agent-frontend` fails at [`LLMRouter.ts:144`](../apps/frontend/src/services/LLMRouter.ts#L144) because `rejectReady` is unused. This workspace is not included in the primary client build workflow, so its failure was not caught by the release pipeline.

**Recommendation:** Remove or use the variable, and add this workspace build to CI if it remains a supported app surface.

### Medium: Initial client bundle is large

The primary build emitted a 1.67 MB main JavaScript chunk (472.47 kB gzip) and a 6.14 MB worker. Vite reported chunks over its 500 kB threshold. The PWA precache contains 37 entries totaling about 11.4 MB; the full `client/dist` directory is about 31 MB.

**Impact:** Cold startup, update downloads, and storage use may be slow on mobile networks and lower-end devices.

**Recommendation:** Lazy-load the avatar and AI features where possible, and review whether the worker and model-related assets need to be in the initial app download.

## Release and device limitations

- The iOS release has no installable IPA because Apple signing is not configured. The Xcode archive is available as a GitHub Actions artifact; installing on a device requires a signed IPA distributed through TestFlight or the App Store.
- The Android workflow builds a debug APK when no Android keystore secrets are configured. Confirm release signing before Play Store distribution.
- No physical Android or iOS device was available for permission, speech, call, offline-model, or app-resume tests.
- No interactive browser session or automated end-to-end suite was run. The repository has build/type-check workflows but no dedicated unit, component, or browser test suite.

## Recommended order

1. Protect provider-backed API routes with authentication, quotas, and rate limits.
2. Triage the client production dependency advisories, starting with the critical/high transitive packages.
3. Fix the secondary frontend TypeScript error or remove that workspace from the supported app surface.
4. Add automated browser smoke coverage and native device checks for permissions, voice, offline mode, and downloads.
5. Configure Apple and Android release signing if store-installable packages are required.
6. Reduce initial JavaScript and PWA precache weight for mobile startup.
